01 — Context

The problem

A logistics station receives hundreds of orders each morning. Someone has to decide which orders travel together, how many vehicles are needed, who drives each one, and in what order the stops are visited — all before dispatch, and all under real constraints: vehicle capacity, customer time windows, rider shift limits, and zone rules.

That decision was largely manual. My work was to automate it end to end, for both first-mile (pickups flowing into the hub) and last-mile (deliveries flowing out) in a single unified pipeline rather than two separate systems.

The hard constraint was that a middle-mile system was already live and carrying real freight. Nothing I shipped could change its behaviour. Every new path was written as an additive branch behind a per-station feature flag, defaulting off — so rollback was flipping one switch, and the running system never noticed the new code existed.

Design rule Additive, never mutating. New endpoints and branches beside the existing ones — never an edit to a live code path.

02 — Contribution

What I built

Four pieces, from the optimization core out to the operator-facing flows.

◆

Route optimization solver

The sequencing core: given a set of tasks and available vehicles, decide which vehicle serves which stops and in what order. Built as a construction heuristic that seeds an initial solution, then a Large Neighborhood Search optimizer that repeatedly destroys and repairs parts of the plan to escape local minima.

  • Nearest-insertion
  • LNS + simulated annealing
  • Capacity
  • Time windows
  • Shift limits
◈

Solver variants

One engine was not enough for every trip shape. I worked across a time-dependent variant that uses real road-network travel times instead of straight-line distance, and a pickup-and-delivery (PDPTW) path that keeps a pickup before its matching drop on the same vehicle.

  • Time-dependent matrices
  • PDPTW
  • Road-network ETAs
▦

Planning & dispatch workflow

The orchestration layer the console runs on: generate a plan, review the proposed routes, assign riders and vehicles, dispatch the bin, then track it live. Every mutating call is idempotent and station-scoped, and degrades with an explicit reason instead of failing blind when a dependency is unavailable.

  • Plan → review → assign
  • Dispatch
  • Live tracking
  • Feature-flagged
↻

Mid-day change handling

Plans go stale the moment reality moves. I designed the flows for dynamic order injection (new orders arriving after planning) and reassignment (a rider goes no-show), plus no-show detection and ETA recompute so the board reflects the truth rather than the morning's assumption.

  • Order injection
  • Reassignment
  • No-show detection
  • ETA recompute
Honest scope note. Injection and reassignment are designed and orchestrated — the flows, contracts and safeguards exist and are wired end to end. True incremental insertion into an already-solved route needs solver support that did not exist yet, so injection currently degrades to a full re-solve and flags itself as degraded rather than silently pretending to be incremental.
